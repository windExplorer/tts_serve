## 2. 为什么要替换 CosyVoice3

原链路在 AstrBot 插件项目中：

```
e:/WP-V2/Mine/astrbot_plugin_cosyvoice
  ├─ main.py                     # 钩子、指令、工具
  ├─ core/tts_engine.py          # 文本清洗、分段、合成调度
  ├─ cosyvoice/client.py         # HTTP 客户端
  ├─ deploy/cosyvoice_api.py     # FastAPI 服务
  └─ voices/                     # 音色映射
```

模型源码目录：

```
d:/AI/CosyVocie/CosyVoice        # 注意实际拼写是 CosyVocie
```

### 2.1 速度问题根因

| 环节 | 证据 | 影响 |
|---|---|---|
| 插件全局并发默认 1 | `main.py:66-69` | 多段/多用户串行 |
| 服务端全局锁串行 | `deploy/cosyvoice_api.py:47-50` | 单模型一把锁 |
| 模型非流式 | `deploy/cosyvoice_api.py:185-189` 固定 `stream=False` | 必须等整段生成完才返回 |
| 每段独立推理 | `core/tts_engine.py:495-524` | 段数越多 HTTP/推理次数越多 |
| 重复加载参考音频 | 每个请求都解析 `prompt_wav` | 多段时重复开销 |
| 每次推理后清 CUDA cache | `cosyvoice/cli/model.py:240-242` | 多段额外耗时 |

### 2.2 质量问题根因（标点被跳过、连读、意思变）

按嫌疑排序：

1. **分段把句子切碎，段间无上下文**
   - `split_by_newline=true` 默认按换行硬切。
   - `segment_len=0` 时按 `。！？!?\n` 切，超 200 字硬切。
   - 若开启 `segment_len`，默认 `segment_punct` 还包含 `，、；：`。
   - **每段都是独立 zero-shot 推理**，`segment_merge=true` 只是拼 PCM，不恢复上下文。

2. **`prompt_text` 与 CosyVoice3 的 `<|endofprompt|>` 机制冲突**
   - 插件 `_looks_polluted` 会丢弃含 `<|...|>` 的参考文本。
   - CosyVoice3 `_ensure_endofprompt` 会自动补：
     `You are a helpful assistant.<|endofprompt|>`
   - 结果：参考文本不再与音频逐字对应，音色/语气/停顿不稳。

3. **CosyVoice 前端文本归一化改标点**
   - `.` → `。`
   - 括号删除、破折号变空格
   - 尾部 `，,、` → `。`
   - `split_paragraph(..., merge_len=20, comma_split=False)` 合并短句
   - 过滤纯标点片段

### 2.3 关于“不分段”的结论

- **对连贯性和语义，越少分段越好**；对首包速度，分段有价值。
- 但插件里的“整段”（`/tts0`、`segment_merge=true`）内部仍会 `split_text` 后逐段推理再拼 PCM。
- 判断到底分没分，看日志 `合成 i/N` 最直接。
- 暂存建议（Qwen3 上仍需验证）：按句号/大段切，段长 80~120，不要把逗号当切点；`split_by_newline` 视情况关闭。

## 3. 选型决策

### 3.1 候选模型对比（结合本机与需求）

| 模型 | 结论 | 原因 |
|---|---|---|
| **Qwen3-TTS-12Hz-0.6B-Base** | ✅ **首选** | Apache-2.0、3 秒克隆、低延迟、速度快、许可友好、队列/轮班加载更合适 |
| Qwen3-TTS-12Hz-1.7B-Base | 后续候选 | 质量更好，但慢约 20%~35%；显存/加载更重 |
| Fun-CosyVoice3-0.5B | 保留回退 | 存量可用，但正是本次要替换的对象 |
| IndexTTS2 / 2.5 | 暂不纳入 | 中文情感口碑好，但显存/许可/速度不占优 |
| Fish Speech S2 4B | 排除 | 太大且 Research License 非商用 |
| VoxCPM2 2B | 排除 | 更慢，48kHz 输出开销大 |
| F5-TTS 0.3B | 排除 | 中文错字率、停顿不自然，与本次痛点重合 |
| GPT-SoVITS | 排除 | 吞句/幻觉问题与本次痛点重合 |

### 3.2 为什么 0.6B 而不是 1.7B

公开口径与社区实测趋势一致：

- 首包延迟几乎一样：0.6B 约 **97ms**，1.7B 约 **101ms**。
- 整体生成速度 0.6B 快约 **20%~35%**：
  - RTF 0.288 vs 0.313（并发 1）
  - 技术报告 25Hz：0.234 vs 0.253
  - 社区实测生成 10 秒音频：约 1.2s vs 1.8s
- 队列吞吐更高：H100 约 125 req/s vs 92 req/s。
- 与 ComfyUI 轮班时，0.6B 权重更小，冷加载更快。

**结论：先上 0.6B；如果质量不够再评估 1.7B。**
